## Findings

### F01 ? Misleading activity description after denied/failed writes ? FAIL

A denied chat note returned `action_failed`, created no file, and correctly stored an audit row with `denied_by_user / not_executed`. Nevertheless, the workspace activity row said:

```json
{"what_happened":"Saved a personal note","permission_note":"denied_by_user","status":"not_executed"}
```

`what_happened` is selected solely by tool name [S13]. The same design affects failed writes. This is a truthful-reporting defect even though the adjacent status and chat response are accurate. Evidence: `http-evidence.json`, scenario `denied activity description truthful`.

### F02 ? Direct approval omits completion events ? FAIL

A real approved note was saved, but the event bus contained only:

```text
permission.requested
permission.approved
tool.started
```

There was no `tool.completed` or `task.completed`. The direct-action return occurs before completion emission [S14]. This leaves event subscribers without the successful terminal notification required by the event-driven design (ADR-002/009). Evidence: `event-followup.json`.

Verification correction: the first component probe used a nonexistent `all_events` accessor and incorrect underscore-form event names. Its last row is **invalid evidence** and is not counted. A separate fresh probe used the actual `published_events` property and dotted event names; that valid observation is the one reported above. The original evidence was preserved rather than overwritten.

### F03 ? Revocation is stale across overlapping runtime instances ? FAIL at deployment boundary

Two runtime containers were opened against one isolated data directory. Runtime A obtained an approved note stamp. Runtime B revoked `notes.create_note` and persisted it. Runtime A then executed the old stamp successfully and created `synthetic.md`.

Direct SQLite inspection simultaneously showed the global revocation in `permission_policy` and `success` in the authorization and audit records. Policy is loaded once into each instance [S10]; the executor rechecks that in-memory copy [S8], not the latest persisted policy. The SQLite claim remains single-use, but it does not solve stale policy.

This is **one observed unauthorized side effect in the exploratory overlapping-runtime scenario**. The ADR's single-process v1 target limits its deployment relevance; the normal one-runtime tests had zero unauthorized side effects. No single-runtime ownership guard was found in runtime construction [S12]. An unrestricted ?no permission bypass? claim is therefore not supported. Evidence: `component-evidence.json`, `two-instances` observation in the recorded verification output; reproduction script included.

### F04 ? Some rejected execution attempts leave no audit record ? FAIL for complete audit coverage

Forged-token, wrong-task, and post-approval revocation attempts were rejected with zero writes, but their databases had **zero tool audit rows** and still showed an `approved` authorization. The rejection occurs in stamp verification or claim checks before the executor's audited handler path [S7?S9]. This does not permit execution, but it prevents reconstructing these attempted violations from NOVA's audit API. Evidence: `rejection-audit.json` and `component-evidence.json`.
